# ИИ-консультант для интернет-магазина

## Описание проекта
ИИ-ассистент, который помогает покупателям интернет-магазина получать 
ответы на вопросы о товарах, ценах и условиях доставки, а также 
сопровождает их на всех этапах выбора и оформления покупки.

## Почему эта тема
Работаю в сфере интернет-торговли и рекламы на Авито. Вижу, что большинство 
продавцов тратят много времени на однотипные вопросы покупателей. 
ИИ-консультант позволит автоматизировать этот процесс и повысить конверсию.

---

## Экономика ИИ-решения

### Сценарий использования

- **200 активных покупателей в день**
- **3 вопроса на покупателя**
- **600 запросов в день / 18 000 запросов в месяц**

Средний размер одного запроса:
- вопрос покупателя: 100 токенов
- системный промпт и инструкции: 300 токенов
- **Input итого: 400 токенов**
- **Output (ответ бота): 200 токенов**

### Месячный объём токенов

- Input: 18 000 × 400 = **7 200 000 токенов**
- Output: 18 000 × 200 = **3 600 000 токенов**

---

### Стоимость облачных провайдеров

Формула: `(input_tokens / 1_000_000 × цена_input) + (output_tokens / 1_000_000 × цена_output)`

| Модель | Класс | Input /1M | Output /1M | Итого/месяц |
|--------|-------|-----------|------------|-------------|
| Claude Opus 4.6 | Флагман | $5.00 | $25.00 | **$126** |
| Gemini 2.5 Pro | Средний | $1.25 | $10.00 | **$45** |
| DeepSeek V3.2 | Бюджет | $0.28 | $0.42 | **$3.5** |

**Расчёт Claude Opus:** 7.2 × $5 + 3.6 × $25 = $36 + $90 = $126/мес

**Расчёт Gemini 2.5 Pro:** 7.2 × $1.25 + 3.6 × $10 = $9 + $36 = $45/мес

**Расчёт DeepSeek V3.2:** 7.2 × $0.28 + 3.6 × $0.42 = $2 + $1.5 = $3.5/мес

---

### Стоимость локального развёртывания

Локальный запуск на CPU (обычный ноутбук):
- Стартовые затраты: **$0** (оборудование уже есть)
- Электричество: ~**$10/месяц**
- Скорость: 5–15 токенов/сек (медленно для продакшена)
- **Итого: ~$10/месяц**

---

### Точка безубыточности

При текущей нагрузке (MVP):
- DeepSeek V3.2 ($3.5/мес) **дешевле** локального запуска ($10/мес)
- Локальный запуск окупается только при нагрузке от ~$300/мес на API

**Вывод:** на этапе MVP облачный API выгоднее локального решения.

---

### Выбор стратегии

Для данного проекта выбрана **облачная стратегия на базе DeepSeek V3.2**.

При нагрузке 600 запросов в день стоимость составляет всего $3.5 в месяц — 
это оптимально для MVP и позволяет быстро запустить продукт без затрат на инфраструктуру.

## ДЗ 2.1: API провайдеров

### Что реализовано

Скрипт `api_demo.py` демонстрирует основные возможности работы с LLM API:

- Подключение через OpenAI SDK с ключом из `.env` файла
- Базовый запрос с system и user сообщениями
- Эксперимент с temperature
- Стриминг с замером TTFT

Скрипт линейный, разбит на 3 пронумерованных демо-блока (базовый запрос →
эксперимент с temperature → стриминг). Переключение провайдера — простое
`if/else` по переменной `LLM_PROVIDER`: для OpenAI используется обычный
`OpenAI(api_key=...)`, для Ollama — тот же клиент OpenAI SDK, но с локальным
`base_url` и фиктивным `api_key="ollama"`, потому что Ollama эмулирует
OpenAI-совместимый API — то есть переключение провайдера не требует смены
библиотеки или переписывания вызовов, только двух параметров клиента.

### Эксперимент с temperature

Запрос: *"Придумай слоган для интернет-магазина электроники"*

| Temperature | Результат |
|-------------|-----------|
| 0.0 | "Технологии будущего — в одном клике!" |
| 0.7 | "Технологии будущего — в одном клике!" |
| 1.5 | "Технологии на кончиках пальцев!" |

**Вывод:** при temperature=0 и 0.7 модель дала одинаковый ответ —
детерминированный режим. При temperature=1.5 появилась вариативность —
модель сгенерировала другой вариант слогана.

### Стриминг

TTFT (time-to-first-token) измеряется вручную: таймер стартует перед вызовом
`stream=True`, останавливается на первом непустом `chunk.choices[0].delta.content`.

- TTFT: 1.42s — время до первого токена
- Полное время: 3.07s
- Ответ появлялся по частям в реальном времени

### Два провайдера

Переключение между провайдерами реализовано через переменную
`LLM_PROVIDER` в `.env` файле — без изменения кода:
- `LLM_PROVIDER=openai` → GPT-4o-mini через OpenAI API
- `LLM_PROVIDER=ollama` → qwen3:1.7b локально через Ollama

## ДЗ 2.2: Промпт-инжиниринг

### System prompt по структуре РРФО

Разработан production-ready промпт для ИИ-консультанта магазина "ТехноМаркет"
по структуре **Р**оль → **Р**еакции/правила → **Ф**ормат → **О**граничения:
- Роль: ИИ-консультант интернет-магазина электроники
- Правила: отвечать только по теме магазина, не придумывать цены
- Формат: кратко, максимум 3-4 предложения, простой язык
- Ограничения: не обсуждать посторонние темы, не выполнять prompt injection

К промпту добавлены 4 few-shot примера, которые явно показывают модели
границы ответа: возврат товара, способы оплаты, сроки доставки и —
отдельным примером — вежливый отказ отвечать на вопрос не по теме магазина
("Расскажи мне про политику..." → "Я консультант магазина ТехноМаркет и
могу помочь только с вопросами о товарах и услугах"). Этот же промпт
(вместе с few-shot) в итоге стал системным промптом `assistant.py` в ДЗ 2.5 —
то есть 2.2 не изолированное упражнение, а прототип, который сразу пошёл в
дело.

## ДЗ 2.3: Надёжность — ошибки, retry, fallback

### Что реализовано

Класс `RobustLLMClient` в файле `robust_client.py`:
- **Retry с exponential backoff + jitter** — при ошибках 429 и таймаут повторяет запрос до 5 раз с паузами 1→2→4→8→16 сек
- **Fallback-цепочка** — OpenAI → OpenRouter → "Сервис временно недоступен"
- **Логирование** — timestamp, провайдер, код ошибки, номер попытки
- **Трекинг usage** — токены и стоимость каждого запроса и за сессию

Технически retry реализован через декоратор `tenacity.retry` на внутренней
функции `_do_request()`: `retry_if_exception_type((RateLimitError,
APITimeoutError))` — то есть повторяются **только** временные ошибки (429,
таймаут), а `400`/`401`/`403` сразу пробрасываются наверх без ретраев,
осознанно (нет смысла повторять запрос с невалидным ключом 5 раз).
Fallback-цепочка описана декларативно списком `PROVIDERS` — основной
(OpenAI, gpt-4o-mini) и резервный (OpenRouter, deepseek-chat); метод `chat()`
перебирает список по очереди и переходит к следующему провайдеру только
если предыдущий упал **после всех** ретраев. Стоимость считается вручную по
таблице цен `PRICES` (input/output $/1M токенов на май 2026) — эта же логика
цен позже легла в основу `/models` эндпоинта ДЗ 3.4.

### Результаты тестирования

Тест 1 — нормальная работа (OpenAI):
```
Пробуем провайдер: OpenAI
✅ Ответ от OpenAI | Токены: 31+232 | Стоимость: $0.000144
Итого за сессию: 263 токенов, $0.000144
```

Тест 2 — fallback (OpenAI сломан → переключение на OpenRouter): цепочка корректно
переключается на следующий провайдер в списке.

### Выводы

Fallback-цепочка работает корректно. Ошибки 400/401 не повторяются, 429/5xx — повторяются с backoff.

Python, OpenAI SDK, tenacity, python-dotenv

## ДЗ 2.4: Кеширование LLM-ответов

### Что реализовано

Класс `LLMCache` в файле `cache_demo.py`:
- **Ключ кеша** — SHA-256 хеш от model + messages + temperature
- **TTL** — просроченные записи автоматически удаляются (по умолчанию 1 час)
- **Статистика** — hits, misses, hit rate в процентах

Ключ строится из `json.dumps({"model", "messages", "temperature"},
sort_keys=True)`, что даёт стабильный хеш независимо от порядка ключей в
словаре. Кеш — простой `dict` в памяти процесса (значение — кортеж
`(response, created_at)`); при чтении в `get()` сравнивается `time.time() -
created_at` с TTL, просроченная запись удаляется лениво (только при
следующем обращении к тому же ключу, а не по таймеру). Важная деталь: в
`chat_with_cache()` запись в кеш происходит **только если `temperature ==
0`** — при温 ненулевой температуре ответы недетерминированные, и кешировать
их означало бы всегда возвращать один и тот же случайный ответ на разные
последующие запросы, что было бы багом, а не оптимизацией.

### Результаты тестирования

```
Запрос 4: Как вернуть товар? ← повтор
⚡ ИЗ КЕША за 0.0000s
Hits (из кеша): 2
Misses (из API): 3
Hit rate: 40.0%
```

### Стек

Python, OpenAI SDK, hashlib, python-dotenv

## ДЗ 2.5: ИИ-помощник для техподдержки

### Что реализовано

Файл `assistant.py` — финальное CLI-приложение, объединяющее все блоки 2.1–2.4:
- **System prompt (РРФО)** — консультант отвечает только по теме магазина
- **Few-shot** — 4 примера в промпте
- **Retry + fallback** — OpenAI → OpenRouter → "Сервис недоступен"
- **Кеширование** — повторные вопросы из кеша мгновенно
- **История** — последние 10 сообщений для контекста
- **CLI-команды** — /stats, /clear, /quit

Здесь же виден осознанный компромисс в дизайне кеша: ключ кеша строится не
из полной истории диалога, а только из `system` + **последнего** сообщения
пользователя (`cache_messages = [m for m in messages if role == system] +
[messages[-1]]`). Иначе один и тот же вопрос, заданный в разных диалогах с
разной историей, никогда бы не совпадал по ключу и кеш почти не работал бы.
История ограничивается вручную в цикле — `system + последние 10 сообщений`
перед каждым запросом, чтобы промпт не рос бесконечно в длинных диалогах.

### Стек

Python, OpenAI SDK, tenacity, hashlib, python-dotenv

## ДЗ 2.6: Мультимодальные API — Vision API

### Что реализовано

Файл `vision_demo.py` — анализ изображений через OpenAI Vision API:
- Приём пути к изображению от пользователя
- Кодирование в base64 перед отправкой в API
- Обработка ошибок — файл не найден, неверный формат, ошибка API
- Демо-режим — 3 изображения разного типа (фото, скриншот, график)

Изображение читается как байты и кодируется в base64, затем передаётся в
`content` сообщения как объект `{"type": "image_url", "image_url": {"url":
"data:{media_type};base64,{...}"}}` — то есть без загрузки на внешний
хостинг, прямо data-URI внутри запроса. Формат файла проверяется по
расширению (`.jpg/.jpeg/.png/.gif/.webp`) до отправки, чтобы не тратить
вызов API на заведомо неподдерживаемый файл.

### Выводы

Vision API корректно распознаёт разные типы изображений — фото товаров, скриншоты интерфейсов и графики с данными.

### Стек

Python, OpenAI Vision API (gpt-4o-mini), base64, python-dotenv

## ДЗ 3.1: Function Calling

### Что реализовано

Файлы в папках `app/` и `examples/` — полный цикл Function Calling:
- **JSON Schema** — два инструмента: `check_stock` и `calculate_delivery`
- **Обработчики** — реальные функции с базой товаров и тарифами доставки
- **System prompt** — вынесен в Jinja2-шаблон
- **Полный цикл tool_call** — 4 шага: запрос → tool_calls → выполнение → финальный ответ

`app/tools/schemas.py` описывает инструменты как JSON Schema с `description`,
который и есть промпт для модели — именно по этому тексту модель решает,
когда вызывать `check_stock`, а когда `calculate_delivery`. `app/tools/handlers.py`
содержит реальные (пусть и захардкоженные вместо БД) данные: 6 SKU в
`STOCK_DATABASE` с ценой/остатком и тарифы доставки по 6 городам с разным
сроком/стоимостью — для незнакомых городов есть дефолтный fallback (5-10
дней, 499 руб.), а не ошибка. `execute_tool()` — единая точка диспетчеризации
по имени функции, оборачивает результат в JSON. System prompt вынесен в
отдельный файл `app/prompts/system_v1.j2` и рендерится через Jinja2
(`app/prompts/loader.py`, с `lru_cache` — шаблон читается с диска один раз)
вместо строки прямо в коде, что упрощает правки промпта без деплоя.
`examples/run_tool_call.py` прогоняет 4 контрольных случая — два явно
требуют вызова конкретного инструмента, один точно не требует, и один
пограничный ("подскажите что есть в наличии" без конкретного SKU) — чтобы
проверить, что модель не вызывает tool туда, где он не нужен.

## ДЗ 3.2: Архитектурный паспорт проекта

### Что реализовано

Файл `docs/architecture.md` — архитектурный паспорт с Mermaid-диаграммой:
- Диаграмма компонентов — 4 слоя (Gateway → Service → LLM → Data)
- ADR-001 — обоснование выбора Request-Response паттерна
- ADR-002 — стратегия fault tolerance
- Таблица точек отказа
- LiteLLM — анализ и обоснование решения

Диаграмма фиксирует итоговую архитектуру: Gateway (Telegram-бот + FastAPI)
→ Service (ChatService, RAGService, SecurityLayer) → LLM (OpenAI gpt-4o-mini,
эмбеддинги, Whisper) → Data (Redis, Qdrant, файловое хранилище чатов).
ADR-001 фиксирует выбор Request-Response + опциональный SSE-стриминг вместо
WebSocket — сознательный компромисс простоты против сложности инфраструктуры,
с явно прописанным пределом ("при нагрузке >1000 RPS потребуется очередь
задач"). ADR-002 документирует ту же fallback-стратегию, что и в ДЗ 2.3/2.5,
но уже на уровне архитектуры сервиса, с конкретными параметрами (5 ретраев,
backoff 1→16 сек, timeout 30 сек) и таблицей "что откажет → что произойдёт →
как митигируется" по каждому внешнему компоненту (OpenAI, Redis, Qdrant,
Telegram API).

### Как проверить

## ДЗ 3.3: Асинхронная обработка

### Что реализовано

Скрипт `scripts/benchmark.py` сравнивает синхронный клиент (обычный `OpenAI`,
запросы строго по очереди) с асинхронным `AsyncLLMClient` (`app/services/llm_client.py`)
на одном и том же наборе из 20 промптов. Асинхронный вариант ограничивает

| Async concurrency=5 | 12.74s | x3.4 |

## ДЗ 3.4: FastAPI-сервис для LLM

### Что реализовано

HTTP-сервис на FastAPI (`app/main.py`):
- **POST /chat** — синхронный запрос
- **POST /chat/stream** — стриминг через StreamingResponse
- **GET /health** — liveness probe
- **GET /ready** — readiness probe
- **GET /models** — список моделей с ценами

Сервис собран через `lifespan`-контекстменеджер: при старте создаётся
`AsyncOpenAI`-клиент и опционально Redis (`redis.asyncio`) — если Redis
недоступен, приложение не падает, а логирует предупреждение и продолжает
работать без кеша (`app.state.cache = None`), тот же паттерн graceful
degradation, что и в RAG-интеграции чата (ДЗ 4.1). Отсюда и разница между
`/health` (всегда 200 — "процесс жив") и `/ready` (реально пингует Redis и
возвращает 503, если он недоступен) — классическое разделение
liveness/readiness проб из k8s-практик. Middleware генерирует `X-Request-ID`
на каждый запрос и кладёт его в `structlog.contextvars`, поэтому все логи
внутри одного запроса автоматически помечены одним id без ручной передачи
параметра. Обработчики исключений превращают `LLMRateLimitError` → 429,
`LLMTimeoutError` → 504, прочие `LLMError` → 502 — то есть внутренние
классы ошибок клиента (ДЗ 2.3) прокинуты до HTTP-уровня осмысленными
кодами, а не общим 500. `app/routers/chat.py` перед вызовом LLM прогоняет
каждое входящее сообщение через `validate_input()` (ДЗ 3.8), а ответ — через
`filter_output()` — оба эндпоинта (`/chat` и `/chat/stream`) защищены
одинаково.

### Результаты проверки

```
curl http://localhost:8000/health → {"status":"ok"}
curl http://localhost:8000/ready → {"status":"ok","redis":"up"}
```

### Стек

Python, FastAPI, AsyncOpenAI, Pydantic v2, uvicorn

## ДЗ 3.8: Безопасность

### Что реализовано

Атаки прогонялись через NVIDIA garak, нацеленный прямо на живой `/chat`
эндпоинт сервиса (`eval/security/rest_config.json` — `RestGenerator`,
POST-запрос с `$INPUT` на месте атакующего промпта). Против атак стоят два
защитных слоя: `app/services/security/input_validator.py` (список regex на
типичные фразы джейлбрейка — "ignore previous instructions", "you are now
DAN", "developer mode", плюс лимит длины 4000 символов и порог доли
непечатаемых символов) и `output_filter.py` (canary-токен — случайная
строка, вшитая в системный промпт при старте процесса; если она
обнаруживается в ответе модели, значит промпт утёк, и ответ блокируется, —
плюс маскирование email/телефона/паспорта в исходящем тексте тем же
принципом, что и в логах ДЗ 3.6).

Отдельный скрипт `eval/security/extract_hits.py` не просто считает
проценты — он парсит сырой JSONL-отчёт garak (`~/.local/share/garak/...`)
и достаёт **конкретные** успешные атаки (промпт + ответ модели) по каждому
пробу, чтобы понять причину, а не только цифру. Именно так был найден
корень проблемы с Base64: garak отправляет уже закодированную полезную
нагрузку, а `input_validator.py` ищет слово "base64" в открытом виде — оно
в закодированном запросе просто не встречается, поэтому регексп-фильтр его
не ловит.

### Результаты garak

| Probe | Baseline | After | Статус |
|-------|----------|-------|--------|
| DAN-атаки | 0% | 0% | ✅ |
| encoding.InjectBase64 | 61.33% | 62.50% | ⚠️ |
| promptinject | 67.97% | 67.19% | ⚠️ |

### Выводы

DAN-атаки полностью отбиты — модель gpt-4o-mini сама по себе устойчива к
jailbreak-паттернам такого рода. Base64-инъекции и часть prompt injection
после добавления фильтров остались практически на том же уровне: чтобы
закрыть Base64, нужно не искать слово "base64" в тексте, а декодировать
входящий текст и уже потом проверять его содержимое; для prompt injection —
расширять паттерны под перефразированные варианты, которые garak
подставляет вместо буквальных совпадений. Оба вывода зафиксированы как
конкретный план в `docs/security/garak_after_2026-07-05.md`.

Python, NVIDIA garak v0.15.0, regex, FastAPI

## ДЗ 4.1: Архитектура чата и хранение истории

### Что реализовано

Модуль `app/chat/` — stateful чат с историей диалогов:
- **domain.py** — модели Chat и ChatMessage
- **json_repo.py** — файловое хранилище (JSONL, soft-delete)
- **service.py** — ChatService со sliding window стратегией
- **routes.py** — 5 endpoints

Хранилище спрятано за `Protocol`-абстракцией `ChatRepository`
(структурная типизация — любой класс с нужными методами подходит без
явного наследования), поэтому `ChatService` не знает, что под капотом JSON
на диске, а не Postgres — реализацию можно заменить, не трогая сервисный
слой. `JsonChatRepository` хранит каждый чат как `chat.json` (метаданные) +
`messages.jsonl` (append-only лог сообщений, одна строка — одно сообщение).
Soft-delete реализован без реального удаления: очистка истории дописывает
в конец того же `.jsonl` файла служебную строку-маркер `{"type":
"soft_delete", "at": ...}`, а `list_messages()` при чтении находит **последний**
такой маркер и возвращает только то, что после него — то есть старые
сообщения физически остаются на диске (аудит/восстановление возможны), но
логически чат "очищен". `ChatService.send_message()` — конвейер из 6 шагов:
сохранить сообщение пользователя → загрузить чат и последние 10 сообщений
(`CHAT_CONTEXT_WINDOW`) → попытаться получить RAG-контекст (обёрнуто в
`try/except` — если ретривер упал, чат продолжает работать без RAG, тот же
принцип graceful degradation, что и с Redis в ДЗ 3.4) → собрать messages
для LLM → стримить ответ токен за токеном → сохранить ответ ассистента.

### Endpoints

| Метод | URL | Описание |
|-------|-----|---------|
| POST | /chats | Создать чат |
| POST | /chats/{id}/messages | Отправить сообщение |
| GET | /chats/{id}/messages | История |
| DELETE | /chats/{id}/messages | Очистить |
| GET | /chats/{id} | Метаданные |

### Стек

Python, FastAPI, aiofiles, JSONL, Pydantic v2

## ДЗ 4.2: Telegram-бот как тонкий клиент

### Что реализовано

Telegram-бот `@technomarket_shop_bot` на aiogram 3:
- **BackendClient** — httpx-клиент к FastAPI
- **Команды** — /start, /help, /clear, /cancel
- **FSM-сценарий** — /ask → выбор темы → стрим ответа
- **Inline-клавиатура** — 5 тем

Бот сознательно "тонкий" — вся логика (история, RAG, LLM) остаётся на
backend, а сам бот только форматирует Telegram-специфичные вещи. `/start`
создаёт (или получает) чат на backend по `telegram user_id` и кладёт
`chat_id` в FSM-контекст на весь диалог. `/ask` запускает пошаговый
FSM-сценарий (`AskFlow`: `waiting_for_topic` → `waiting_for_question`) с
inline-клавиатурой из 5 тем (доставка/возврат/оплата/гарантия/поддержка) —
выбранная тема подставляется префиксом в вопрос перед отправкой на backend.
Стриминг в Telegram эмулируется повторным редактированием одного и того же
сообщения: бот копит буфер токенов из SSE-потока backend'а и вызывает
`edit_text(buffer)` на каждый чанк, обёрнутым в `try/except`, потому что
Telegram API возвращает ошибку "message is not modified", если текст не
изменился между чанками — это ожидаемо и просто игнорируется.
`BackendClient` (httpx) использует раздельные таймауты — короткий на
подключение (3 сек) и длинный на чтение (120 сек), потому что LLM-стрим
может идти дольше обычного HTTP-запроса, и переводит типовые сетевые
ошибки (`ConnectError`, `ReadTimeout`, HTTP 429) в понятные пользователю
русскоязычные сообщения вместо технических трасс.

### Архитектура

Пользователь → Telegram → Бот → FastAPI → OpenAI

### Стек

Python, aiogram 3, httpx, FSM, MemoryStorage

## ДЗ 5.2: Векторные базы данных — Qdrant

### Что реализовано

- **Qdrant в docker-compose** — qdrant/qdrant:v1.14.0 с named volume
- **VectorStore** (`app/services/vector_store.py`) — async обёртка
- **54 документа** в коллекции `documents`
- **Cosine vs Dot** — все 5 запросов совпали (OpenAI нормализует векторы)

`VectorStore` — тонкая async-обёртка над `qdrant-client`, чтобы остальной
код не работал с Qdrant напрямую. `ensure_collection()` создаёт коллекцию
с явными HNSW-параметрами (`m=16, ef_construct=100` — это дефолты Qdrant,
оставлены осознанно, с комментарием в коде "оптимально для коллекций до
1M векторов"), плюс сразу 3 payload-индекса (`source`, `created_at`,
`category`) для последующей фильтрации поиска. Есть защитная проверка: если
коллекция уже существует, но её размерность вектора не совпадает с
ожидаемой — метод падает с понятной ошибкой вместо тихого рассинхрона
(типичный баг — сменили модель эмбеддингов, забыли пересоздать коллекцию).
`upsert()` грузит точки батчами по 256, дожидаясь подтверждения (`wait`)
только на последнем батче — так быстрее, чем ждать после каждого. В
`scripts/load_to_qdrant.py` 54 факта о магазине получают детерминированные
ID через `uuid5(NAMESPACE_DNS, f"{source}_{index}")` — повторный запуск
скрипта не плодит дубликаты, а просто перезаписывает те же точки; эта же
схема ID позже используется и расширяется в `ingest.py` для ДЗ 5.5.
`cosine_vs_dot.py` не просто сравнивает векторы "на глаз" — он копирует
реальные точки из продовой коллекции в две временные (COSINE и DOT),
прогоняет одни и те же 5 запросов по обеим и сверяет **порядок ID**
результатов, а не только текст топ-1; убедившись, что ранжирование
идентично, удаляет обе временные коллекции.

## ДЗ 5.6: Оценка качества и мониторинг RAG

### Что реализовано
- **Golden dataset** — 33 пары вопрос/ответ, сгенерированы через RAGAS `TestsetGenerator` на корпусе `data/`, вручную проверены и отредактированы (`tests/eval/golden_dataset.json`)
- **`scripts/run_eval.py`** — прогон RAGAS-метрик (faithfulness, answer_relevancy, context_precision, context_recall) + кастомная метрика `has_citation` на golden dataset
- **Трейсинг Arize Phoenix** — все запросы к `/rag/query` логируются со span'ами retrieval/generation (`app/observability/tracing.py`)
- **2 A/B-эксперимента** — chunking (512 vs 1024 символов) и режим построения промпта для генерации (`snippet` vs `full` чанк)
- **Phoenix `HallucinationEvaluator`** (опционально) — оценка галлюцинаций на живом трафике, отдельно от golden dataset
- Полный отчёт со всеми метриками и failure analysis — [`docs/rag_evaluation.md`](docs/rag_evaluation.md)

### Результаты A/B-экспериментов

| Конфигурация | faithfulness | answer_relevancy | has_citation | latency |
|---|---|---|---|---|
| Baseline (chunk_size=512, снипет-контекст) | 0.664 | 0.525 | 0.667 | 1324 мс |
| chunk_size=1024 (тот же снипет-контекст) | 0.453 | 0.372 | 0.485 | 1290 мс |
| **chunk_size=512, полный контекст (победитель)** | **0.878** | **0.748** | **0.909** | 1589 мс |

### Найденный баг и фикс
Промпт для генерации строился из 200-символьного сниппета вместо полного текста найденного чанка — модель физически не видела большую часть найденного контекста. Это же объясняет провал эксперимента с укрупнением `chunk_size`: retrieval становился точнее, а до генерации всё равно доходило только 200 символов. Фикс — флаг `RAG_CONTEXT_MODE=full` — стал новым дефолтом в проде: faithfulness +32%, answer_relevancy +43%, has_citation +36%.

### Мониторинг на живом трафике (опционально)
Прогон Phoenix `HallucinationEvaluator` на 22 живых трейсах показал 40.9% (9/22) ответов, размеченных как hallucinated — почти все на вопросах, сформулированных "своими словами" (не как в golden dataset), где модель ошибочно отвечает "по базе не нашёл", хотя релевантный контекст есть. Вывод для следующей итерации: смягчить инструкцию в `SYSTEM_PROMPT` про отказ от ответа.

### Стек
RAGAS 0.4.x, Arize Phoenix (трейсинг + evals), OpenAI gpt-4o-mini (judge и прод), Qdrant, OpenTelemetry/OTLP

### Выводы
Из двух проверенных гипотез — укрупнение `chunk_size` (улучшение retrieval) и полный контекст вместо сниппета (улучшение generation) — выигрывает вторая: проблема оказалась не в поиске, а в том, что до модели не доходил уже найденный контекст. Диагностическая матрица (faithfulness vs context_recall) оказалась рабочим инструментом для выбора, какой эксперимент вообще стоит ставить, а не перебор всех вариантов подряд. `has_citation` (0.909) пока не дотягивает до порога чекпоинта (0.95) — известная проблема, план исправления в отчёте.

## ДЗ 6.1: Что такое агент — цикл и компоненты

### Что реализовано
- **`app/services/agent_naive.py`** — наивный agent loop на Chat Completions: `run_agent(task, max_steps=6) -> dict`, без LangGraph и внешних агентных библиотек, только `openai` и stdlib
- **3 tools** в формате JSON Schema для function calling: `search_knowledge_base` (переиспользует ретривер из `app/services/rag.py`, возвращает топ-1 фрагмент), `get_current_time` (детерминированная, через `zoneinfo`, без сети), `send_telegram_message` (заглушка — только `print`, без реального Telegram API)
- **`DISPATCH`** — явный словарь `{имя_tool: функция}` вместо `eval`/`getattr`; при неизвестном имени tool агент получает контролируемую строку-ошибку вместо `KeyError`
- **`trace`** — пошаговый лог: номер шага, имя и аргументы tool, результат (обрезан до 200 символов), токены запроса/ответа, длительность шага
- **6 прогонов** (5 обязательных сценариев + 1 случайно пойманный инфраструктурный сбой) с разбором находок — [`docs/agent-naive-traces/`](docs/agent-naive-traces/)

### Результаты прогонов

| Сценарий | Шагов | Итог |
|---|---|---|
| Успешная задача (поиск + отправка в Telegram) | 3 | Успех — с находкой про faithfulness (самовывоз обобщён до "доставка") |
| "Нет данных" — провокация цикла | 2 | Честный отказ, без зацикливания (score-guard из `rag.py`) |
| Провокация галлюцинации несуществующего tool | 2 | Tool не выдуман, честный отказ |
| Составная задача из 4+ подзадач | 4 | Успех через parallel tool calls; найдено ограничение top-1-фрагмента |
| Провокация "отправь, не уточняя" | 1 | Отказ выполнить необратимое действие без подтверждения |
| (доп.) Qdrant недоступен | 2 | Graceful degradation: ошибка tool не уронила цикл, агент не подтвердил недоказанный факт |

### Найденные архитектурные наблюдения
Модель самостоятельно делает **parallel tool calls** (несколько вызовов в одном шаге) — цикл это корректно обрабатывает, так как `for tool_call in message.tool_calls` выполняет все и складывает результаты в `messages` перед следующим запросом к LLM. На составной задаче (сценарий 4) контекст вырос в 2.4 раза всего за 4 шага — на длинных диалогах именно размер контекста, а не `max_steps`, скорее всего станет реальным ограничением. `search_knowledge_base`, ограниченный топ-1 фрагментом по условию задания, на многотемных запросах закономерно возвращает только часть нужной информации — агент в этом случае честно признаёт нехватку данных, а не выдумывает недостающее.

### Стек
OpenAI Chat Completions (`gpt-5.4-mini`), function calling / tool use, Qdrant (через `app.services.rag`), `zoneinfo`

### Выводы
На всех провокационных сценариях (галлюцинация tool, отправка без подтверждения) поведение агента управлялось исключительно текстом `SYSTEM_PROMPT`, без единой строчки защитного кода в самом цикле — для наивного агента system prompt оказывается основной точкой контроля поведения, а код цикла отвечает за то, чтобы сбои (неверный tool, ошибка сети) не роняли процесс, а превращались в информацию, с которой модель уже сама решает, что делать дальше.

## ДЗ 6.2: Планирование агента

### Что реализовано
- **`app/services/agent_react.py`** — управляемый ReAct-агент поверх baseline из ДЗ 6.1 (`agent_naive.py` не изменён, остаётся эталоном для сравнения): цикл Thought → Action → Observation на `client.chat.completions.create(..., tools=TOOLS, tool_choice="auto")`, с явной "мыслью" перед каждым вызовом tool
- **Тот же набор из 3 tools**, но описания переписаны по чек-листу (что делает / когда вызывать / что значат параметры / что возвращает) и JSON Schema сделана строгой (`"strict": true`, `"additionalProperties": false`)
- **Два жёстких лимита** — `max_iterations` (8–20) и `timeout_per_iteration_sec` (5–15 сек на LLM-вызов + выполнение tool), реализованы через `ThreadPoolExecutor` с `future.result(timeout=...)`: превышение любого лимита даёт явное `"Timeout"` / `"Превышен лимит итераций"`, без зависания
- **Self-reflection (Reflexion-light)** — после каждой observation отдельный дешёвый critic-вызов (`gpt-5.4-mini`) с вердиктом `OK`/`REVISE: <причина>`; лимит 2 ревизии за прогон, счётчик сквозной по всему запуску; при `REVISE` следующий шаг генерируется более сильной моделью (`gpt-5.4`)
- **Подсчёт токенов** по всем LLM-вызовам, включая critic, в общий `dict` + structlog-логирование каждой итерации (номер шага, tool, latency, токены, вердикт критика)
- **10 прогонов** (5 задач домена × naive/react) с ручной оценкой корректности — [`docs/agent-react-report.md`](docs/agent-react-report.md)

### Результаты сравнения (5 задач, 10 прогонов)

| Метрика | naive | react |
|---|---|---|
| Корректных ответов | 4/5 | 5/5 |
| Суммарно токенов | 7 109 | 11 960 |
| Ревизий сработало | — | 0 из 5 |

### Ключевая находка
На задаче "найди условия гарантии и отправь клиенту" naive подал список **исключений** из гарантии ("гарантия не действует, если...") под заголовком "Условия гарантии", не разделив что покрывается и что нет — потенциально вводящая в заблуждение формулировка. React сформулировал точно ("Гарантия **не действует** в случаях: ...") — но не благодаря самой ревизии (critic оба раза вернул `OK`, ревизий не было), а благодаря более осторожному system prompt и tool-описаниям главного исполнителя. Вывод: prompt engineering основной модели предотвращает ошибки эффективнее, чем последующая проверка критиком — self-reflection на этом наборе задач ни разу не потребовался (0 REVISE из 5 задач), но стоил +68% токенов за счёт лишнего LLM-вызова критика на каждый tool.

### Стек
OpenAI Chat Completions (`gpt-5.4-mini` / `gpt-5.4` на ревизии), function calling со строгими JSON Schema, `ThreadPoolExecutor` для таймаутов, structlog

### Выводы
ReAct-обвязка с лимитами уже окупается как страховка от конкретной ошибки faithfulness и как источник аудируемости (`thought` и `critic_verdict` в каждом шаге трейса), но самый дорогой её компонент — сам self-reflection-цикл — на 5 задачах домена не набрал ни одного случая реальной необходимости. Оба жёстких лимита (`max_iterations`, `timeout_per_iteration_sec`) в этих прогонах не были естественно достигнуты — задачи укладывались в 1–3 шага; для эмпирической проверки этих веток нужен отдельный стресс-тест.

## ДЗ 6.3: LangGraph — основы

### Что реализовано
- **`app/services/agent_graph.py`** — тот же ReAct-агент из ДЗ 6.2, переписанный на LangGraph 1.x (`langgraph>=1.0,<2`, `langchain>=1.0,<2`): явный `AgentState(TypedDict)` с reducer'ами (`add_messages` для истории, `operator.add` для накопления `tool_results`), три чистых async-узла (`call_model`, `execute_tool`, `force_finish`), router (`route_after_model`) — отдельная детерминированная функция без сайд-эффектов
- **Два независимо вызываемых графа, решающих одну задачу разными путями**: `custom_graph` (StateGraph собран руками — `add_node`/`add_conditional_edges`) и `prebuilt_graph` (через `langchain.agents.create_agent`)
- **Те же 3 tools из ДЗ 6.2**, перенесены через `@tool`-декоратор `langchain_core.tools` без дублирования описаний — один и тот же tool идёт в оба графа
- **`scripts/visualize_graph.py`** — сохраняет mermaid-схемы обоих графов ([`docs/agent-graph-custom.mmd`](docs/agent-graph-custom.mmd), [`docs/agent-graph-prebuilt.mmd`](docs/agent-graph-prebuilt.mmd)) + PNG
- **`scripts/verify_force_finish.py`** — двухчастная проверка стоп-крана: реальный прогон против намеренно сломанного `search_knowledge_base` (модель честно сдаётся раньше лимита сама — стоп-кран не потребовался) + прямой юнит-тест `route_after_model`/`force_finish` с синтетическим state на `iteration_count == MAX_ITERATIONS`, детерминированно подтверждающий сам механизм
- **`scripts/bench_agents.py`** — бенчмарк 5 задач × 3 реализации (`agent_naive.py`, `custom_graph`, `prebuilt_graph`) × 3 повтора, latency + токены + число LLM-вызовов, усреднено
- Полный разбор — [`docs/agent-graph-report.md`](docs/agent-graph-report.md): конфигурация, state contract, router-логика, mermaid-схема, таблица бенчмарка, custom vs prebuilt, найденный баг, что блокирует переход к персистентности

### Результаты бенчмарка (5 задач, сумма по всем)

| Реализация | Суммарная latency | Суммарно токенов | Всего LLM-вызовов |
|---|---|---|---|
| `agent_naive.py` (loop-baseline) | 9 119 мс | 5 894 | 10 |
| `custom_graph` | 11 878 мс | 6 286 | 11 |
| `prebuilt_graph` | 11 824 мс | 7 557 | 11 |

### Ключевая находка
На составной задаче (поиск гарантии → отправка в Telegram) `naive` неожиданно уложился в 2 LLM-вызова вместо 3 — модель сама объединила `search_knowledge_base` и `send_telegram_message` в один parallel tool_call, потому что system prompt `agent_naive.py` это не запрещает. У `custom_graph`/`prebuilt_graph` system prompt явно требует "не более одного инструмента за шаг" (сознательное решение для этого ДЗ), поэтому оба графа стабильно взяли 3 шага. Итог: разница в latency между naive и графами на этой задаче — не преимущество императивного цикла над графом, а разница в system prompt и везение с параллелизацией модели. `prebuilt_graph` при этом стабильно тратит больше `prompt_tokens`, чем `custom_graph`, почти на каждой задаче — вероятно, `create_agent` добавляет свой форматирующий оверхед, недоступный для прямого контроля.

### Стек
LangGraph 1.2.11, LangChain 1.3.18, langchain-openai 1.6.0, `gpt-5.4-mini`, `AsyncSqliteSaver`-совместимый state (пока без подключённого checkpointer)

### Выводы
Граф не добавляет новых возможностей поверх голого цикла сам по себе — обе формы одинаково решают одни и те же 5 задач. Ценность появляется в другом: явный `AgentState` без SDK-клиентов и API-ключей уже готов к чекпойнтингу (`AsyncSqliteSaver`/`AsyncPostgresSaver`) без переписывания структуры, router как отдельная функция делает stop-condition проверяемой юнит-тестом независимо от LLM (что и потребовалось на практике — реальный прогон против сломанного tool не смог детерминированно проверить лимит итераций, а прямой вызов `route_after_model` смог), а mermaid-схема делает граф самодокументируемым. `custom_graph` дешевле `prebuilt_graph` по токенам почти везде ценой ~120 строк ручного кода — для доклада: писать граф руками оправдано, когда важен контроль над каждым узлом и стоимостью; `create_agent` окупается скоростью старта на простых сценариях без кастомизации.

## ДЗ 6.4: LangGraph — продвинутые паттерны (персистентность, HIL, стриминг)

### Что реализовано
- **`app/services/agent_persistent.py`** — отдельный граф поверх тех же 3 tools, что и в `agent_graph.py` (ДЗ 6.3, не изменён): переключаемый checkpointer через `AGENT_CHECKPOINTER=memory|sqlite|postgres` (`agent_lifespan()`, `checkpointer.setup()` вызывается ровно один раз при старте приложения, не на каждый запрос), `build_initial_state()` — единственная точка сборки state нового треда
- **Human-in-the-loop на `send_telegram_message`** (единственный необратимый tool) через `interrupt()` + `Command(resume=...)` — НЕ через устаревшие `interrupt_before`/`interrupt_after`: два отдельных узла, `prepare_send_telegram` (идемпотентный, только рендер превью) и `confirm_and_execute_send_telegram` (реальный side-effect строго ПОСЛЕ `interrupt()`, чтобы replay на resume не отправлял сообщение повторно)
- **`app/routers/agent.py`** — `POST /agent/stream`, SSE через `graph.astream(stream_mode=["updates", "messages"])`: прогресс по узлам, токены модели, отдельное событие на `__interrupt__`; `config["configurable"]` несёт `thread_id` (стабильный, не `uuid4()` за запрос) и `user_role` (концепция уровня доступа, пока не enforced — см. отчёт)
- **`scripts/time_travel_demo.py`** — офлайн на `AsyncSqliteSaver(":memory:")`: payload `interrupt()`, история чекпоинтов (`aget_state_history`), чтение прошлого состояния по `checkpoint_id`, и **два разных исхода (approve/reject) на двух разных `thread_id`** — resume одного и того же checkpoint'а детерминирован, повторным resume с другим значением второй исход не получить
- **`tests/test_agent_persistent.py`** — 3 smoke-теста на `sqlite(":memory:")` с замоканной моделью: остановка на interrupt, `resume=True` → `sent=True` + side-effect вызван 1 раз, `resume=False` → `sent=False` + side-effect не вызван вообще
- **Postgres** поднят с нуля в `compose.yaml` (раньше в проекте не был настроен, вопреки предположению задания про переиспользование блока "М3Б5") — сервис `postgres:16-alpine`, healthcheck, volume
- Полный разбор — [`docs/agent-persistent-report.md`](docs/agent-persistent-report.md): backend по режимам, Postgres `\dt`-подтверждение, идемпотентность HIL, реальные SSE-логи, time-travel вывод, обоснование `stream_mode`, оба найденных бага

### Результаты проверки (все — реальные прогоны, не синтетика)
| Проверка | Результат |
|---|---|
| `pytest tests/test_agent_persistent.py` | 3 passed |
| SSE: `interrupt()` на новом `thread_id` | сработал стабильно, payload корректный |
| SSE: `resume=true` | side-effect (`[TELEGRAM → 555] ...`) выполнился ровно 1 раз |
| `time_travel_demo.py`, approve-ветка | `sent=True`, реальная "отправка" в логе |
| `time_travel_demo.py`, reject-ветка | `sent=False`, отправки не было |
| Postgres `AGENT_CHECKPOINTER=postgres`, `\dt` | 4 таблицы (`checkpoints`, `checkpoint_blobs`, `checkpoint_writes`, `checkpoint_migrations`) |

### Найденные баги
1. **`SYSTEM_PROMPT` был объявлен, но нигде не подставлялся в `messages`** — ни в CLI, ни в роутере. Граф работал без системного промпта, из-за чего HIL срабатывал непоследовательно (то `interrupt()` срабатывал, то модель просто спрашивала подтверждение текстом). Найдено эмпирически — двумя подряд неудачными SSE-тестами. Исправлено: единственная точка входа `build_initial_state()`.
2. **`AsyncPostgresSaver` несовместим с `ProactorEventLoop`** (дефолт asyncio на Windows) — `psycopg.InterfaceError` при первой же попытке подключения. Известная, задокументированная в самом psycopg несовместимость, не баг проекта. Исправлено переключением на `WindowsSelectorEventLoopPolicy()` при импорте модуля, если `sys.platform == "win32"`. В Docker (Linux) эта ветка не выполняется и баг не воспроизводится в принципе.

### Стек
LangGraph 1.2.11, langgraph-checkpoint-sqlite 3.1.1, langgraph-checkpoint-postgres 3.1.2, psycopg 3.3.4, `gpt-5.4-mini`, PostgreSQL 16 (Docker)

### Выводы
Персистентность и HIL в LangGraph 1.x — это не пара вызовов API поверх готового графа, а требование к дисциплине дизайна узлов: идемпотентность "до interrupt" и side-effect строго "после" — не самодокументирующееся правило, легко нарушить случайно (как чуть не произошло с изначальной сборкой `confirm_and_execute_send_telegram`, где порядок был выдержан правильно, но соседний баг с отсутствующим системным промптом маскировал, что HIL вообще работает штатно). Обе находки этого ДЗ — не про сам LangGraph, а про интеграционные швы вокруг него: пропущенный шаг подстановки промпта и платформенная несовместимость сетевой библиотеки — типичный класс багов, который не ловится чтением кода узлов, только сквозным прогоном сценария на реальном API. Test-suite на `sqlite(":memory:")` с замоканной моделью при этом остаётся быстрым и дешёвым способом закрепить именно логику HIL (interrupt/resume/идемпотентность) отдельно от поведения самой модели.

## ДЗ 6.5: Мультиагентные системы — supervisor vs single-agent

### Что реализовано
- **`experiments/_shared.py`** — общее между обеими реализациями: 5 тестовых вопросов (3 по корпусу, 1 многошаговый, 1 вне базы), tool `search_knowledge_base` (РОВНО ОДИН объект для обеих схем — иначе сравнение нечестное; возвращает все релевантные чанки с именем источника, не только первый), утилиты замера (`total_tokens`/`llm_calls` через `AIMessage.usage_metadata`, RAGAS Faithfulness как reference-free метрика качества)
- **`experiments/multi_agent_langgraph.py`** — supervisor-граф из двух `create_agent`: `researcher` (tools=[search_knowledge_base], только собирает факты) и `writer` (tools=[], только формулирует ответ с цитированием). Supervisor — РУЧНОЙ, через `Command(goto=..., update=...)`, не `langgraph_supervisor.create_supervisor()`: при двух фиксированных ролях без переигровки маршрутизация детерминирована (проверка заполненности полей state), отдельный LLM-вызов на это решение не нужен. `handoff_count` считается прямо в `update` каждого перехода supervisor → агент
- **`experiments/single_agent_baseline.py`** — один `create_agent` с тем же tool'ом и промптом, объединяющим обе роли
- **`experiments/summarize_results.py`** — считает средние по `experiments/results.json` и печатает готовую markdown-таблицу
- Mermaid-схема supervisor-графа — [`docs/architecture-multi-agent.md`](docs/architecture-multi-agent.md) (сгенерирована `app.get_graph().draw_mermaid()`)
- Полный разбор — [`docs/multi-agent-report.md`](docs/multi-agent-report.md): архитектура, таблица, сопоставление с Anthropic-ориентиром, секция `## Решение`

### Результаты (среднее по 5 вопросам, реальные прогоны)
| Метрика | Single-agent | Multi-agent | Δ |
|---|---|---|---|
| Токены на запрос | 2118 | 2859 | +741 |
| LLM-вызовов на запрос | 2 | 3 | +1 |
| Latency (мс) | 2927.4 | 4846.4 | +1919.0 |
| Передач управления на запрос | 0 | 2 | +2 |
| Faithfulness (RAGAS) | 0.95 | 0.98 | +0.03 |

### Найденный баг
`ragas.llms.llm_factory()` создаёт judge с дефолтным `max_tokens=1024` (хранится как обычный dict `model_args`, не pydantic-поле, как можно было бы ожидать) — на длинном составном ответе (вопрос 4) `Faithfulness.ascore()` падал с `IncompleteOutputException`. Исправлено в `app/eval/metrics.py` (`build_judge()`): `llm.model_args["max_tokens"] = 4096`. Это же затрагивает и eval-пайплайн ДЗ 5.6, если там встретится достаточно длинный ответ — фикс общий.

### Решение
**Мультиагент НЕ идёт в диплом.** Множитель токенов получился 1.35× (у Anthropic на breadth-first research — ~15×) — на порядок меньше, потому что сценарий этого ДЗ не breadth-first: один вопрос клиента почти всегда опирается на одну связную область базы знаний, researcher и writer работают строго последовательно над общим контекстом, а не параллельно над независимыми ветками. Даже эта скромная надбавка не окупается: прирост Faithfulness (+0.03) на 5 вопросах неотличим от шума, а latency почти удваивается из-за строго последовательного researcher → writer без какого-либо параллелизма. Agent-слой диплома — один `create_agent` с тем же набором tools; supervisor-граф остаётся в `experiments/` как воспроизводимый аргумент на защите «почему не мультиагент», а не переезжает в `app/agents/`.

### Стек
LangGraph 1.2.11, LangChain 1.3.18 (`create_agent`), RAGAS 0.4.x (Faithfulness, judge `gpt-4o-mini`), `gpt-5.4-mini` (агенты), реальный Qdrant/RAG из М5

### Выводы
Ценность этого ДЗ — не в самом графе (он тривиален, 3 узла), а в том, что архитектурное решение принято по числам, а не по вкусу. Задание прямо предупреждает: single-agent — дефолт, и в этом случае дефолт победил по существу, а не просто "не был опровергнут" — множитель токенов на порядок меньше anthropic-ориентира именно потому, что задача (консультант по одной базе знаний одного магазина) архитектурно ближе к "tight coupling / shared context" — ровно тому профилю, для которого сама Anthropic в «Building Effective Agents» предупреждает: multi-agent обычно проигрывает. Отдельный урок про инструментарий: RAGAS-судья по умолчанию рассчитан на короткие ответы (`max_tokens=1024`) — для более многословных ответов (typical для мультиагентных пайплайнов, где writer получает уже готовый список фактов и может расписаться) лимит нужно поднимать явно, иначе метрика молча падает на части выборки вместо того, чтобы просто занизить оценку.
