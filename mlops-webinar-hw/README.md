# ml-service — MLOps pipeline (credit scoring)

Учебный проект по ДЗ модуля 7 "MLOps без лишней сложности" (Академия EDPRO,
вебинар "От Docker до Evidently: стенд MLOps-конвейера на руках"). Структура
повторяет методичку вебинара: DVC-пайплайн → MLflow (tracking + model
registry + алиасы) → FastAPI-сервис, отдающий предсказания по алиасу модели
→ Evidently (мониторинг дрейфа) → CI в GitHub Actions.

Ветка `webinar-mlops-hw` содержит только это ДЗ, никак не пересекается с
основным проектом (бот поддержки интернет-магазина) в `main`.

## Структура

```
scripts/gen_train_data.py   генерация обучающей выборки (синтетика, seed=42, n=800)
scripts/gen_batch.py        генерация "продового" батча для мониторинга дрейфа (seed=0, n=800)
src/train.py                обучение модели, логирование в MLflow
params.yaml / dvc.yaml      DVC-пайплайн (стадия train)
app/main.py                 FastAPI: /health, /predict?alias=production|staging
monitor.py                  Evidently: отчёт по дрейфу + gate (exit 1 при превышении порога)
build_release_manifest.py   сборка release_manifest.json ("паспорт релиза")
Dockerfile                  образ для app/main.py
.github/workflows/ci.yml    CI: repro пайплайна, drift gate, docker build, smoke-test, публикация в GHCR (только main)
dvc.lock, metrics.json      реальный результат прогона пайплайна
release_manifest.json       паспорт последнего релиза (git SHA + DVC-хэши + MLflow run + Docker-тег)
```

## Как всё собиралось (коротко)

1. Реальный репозиторий вебинара (`romkarus000/ml-service`) — приватный, доступа
   нет. По методичке, полученной от куратора, пересобрана эквивалентная
   структура с нуля (credit-scoring домен, тот же DVC/MLflow/Evidently стек).
2. Первый прогон пайплайна сделан в изолированной облачной песочнице
   (для проверки логики без риска для рабочей машины).
3. Второй, финальный прогон — на отдельном чистом **Ubuntu 22.04 VPS**
   (Timeweb Cloud, 2 vCPU / 2 ГБ RAM), чтобы честно собрать и Docker-образ
   (в первой песочнице сеть блокировала скачивание базовых образов) — весь
   стек поднят и проверен на реальной машине от начала до конца.
4. Ветка `webinar-mlops-hw` создана от `main` в `D:\ai-shop`, файлы
   перенесены на VPS через `git clone`, все дальнейшие шаги (dvc repro,
   MLflow, Docker, Evidently) выполнены там по-настоящему, без имитации
   вывода команд.

## Реальные проблемы по ходу работы и как их чинили

Ничего не выдумано — вот честный список того, что реально ломалось на VPS и
как это диагностировали и чинили:

- **`data/` не сохранилась в git.** Git не хранит пустые директории — при
  клонировании на VPS папки `data/` и `models/` физически не появились,
  скрипт генерации данных упал с `OSError: Cannot save file into a
  non-existent directory`. Починка: `mkdir -p data models` перед первым
  запуском.

- **MLflow-сервер падал по нехватке памяти.** Первый тариф VPS был на
  890 МБ RAM без подкачки. MLflow по умолчанию поднимает 4 uvicorn-воркера,
  каждый грузит pandas/sklearn — сервер стабильно валился в OOM
  (`Child process died` в логе, потом обрыв SSH-сессии целиком). Починка в
  два шага: (1) добавили 1 ГБ swap как временную подушку, (2) итоговое
  решение — увеличили конфигурацию VPS до 2 vCPU / 2 ГБ RAM через
  "Изменить конфигурацию" в панели Timeweb (диск и данные сохранились,
  сервис перезагрузился). После этого MLflow поднимался штатно с дефолтными
  4 воркерами.

- **Docker-образ не собирался в облачной песочнице.** Сетевая политика
  агентской песочницы блокирует скачивание базовых образов с Docker Hub и
  зеркал (`403 Forbidden` и на `registry-1.docker.io`, и на
  `mirror.gcr.io`) — это ограничение инфраструктуры, не баг проекта.
  Именно поэтому финальная сборка и smoke-тест контейнера сделаны на VPS,
  где сеть не резаная.

- **Контейнер не находил модель по алиасу (`No such artifact: ''`).**
  Локальный (не в Docker) FastAPI-процесс успешно грузил модель по алиасу,
  потому что сидел в той же папке, что и `./mlruns` — MLflow tracking-сервер
  отдаёт клиенту не сами файлы модели, а **путь** к ним на диске сервера.
  Контейнер — изолированная файловая система, у него `mlruns/` внутри
  просто нет (в `Dockerfile` копируется только `app/`). Починка: пробросили
  volume с тем же **абсолютным** путём, что записан в MLflow —
  `-v $(pwd)/mlruns:$(pwd)/mlruns` — чтобы путь внутри контейнера совпадал
  с тем, что MLflow хранит у себя в базе.

- **Порт 8000 был занят при первом запуске контейнера.** Локальный uvicorn
  (запущенный раньше для ручной проверки) и контейнер пытались слушать один
  и тот же порт одновременно — контейнер падал на старте с `address already
  in use`. Починка: остановили локальный процесс (`kill %<job>`) перед
  `docker run`.

- **`git push` несколько раз падал с `403 Permission denied`, хотя GitHub
  API подтверждал `push: true`.** Причина — использовался не тот тип
  токена: **fine-grained** Personal Access Token без выданного доступа к
  конкретному репозиторию/без права записи в Contents, тогда как для
  `git push` по HTTPS нужен либо классический токен со скоупом `repo`, либо
  fine-grained с явно настроенными `Repository access` + `Contents: Read
  and write`. Диагностировали через заголовок ответа API
  `X-OAuth-Scopes` (у fine-grained токенов его нет вообще, у классического
  он явно показывает `repo`). После генерации классического токена с
  нужным скоупом пуш прошёл.

- **Коммиты с VPS были подписаны `root@<hostname>`.** На свежем сервере не
  был настроен `git config user.name/user.email`. Починка: настроили
  `git config --global user.name/user.email` под реальные данные (взятые
  из уже существующих коммитов, сделанных с основной машины), и переписали
  историю (`git rebase --exec "git commit --amend --reset-author
  --no-edit"`) для уже созданных коммитов, чтобы автор был единообразным
  во всей ветке.

- **`dvc repro` в самом первом запуске упал на подключении к MLflow** (сервер
  ещё не был поднят к этому моменту) — DVC не успел дописать `.gitignore`
  для уже готовой стадии. Починка: `dvc commit -f` там, где нужно было
  зафиксировать частично успешный прогон без пересчёта.

## Как воспроизвести локально

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
pip install dvc mlflow evidently

dvc init   # если ещё не инициализирован в этой папке (--subdir, если папка — часть большего репо)
mkdir -p data models
python scripts/gen_train_data.py

# в отдельном терминале — поднять MLflow tracking server:
mlflow server --backend-store-uri sqlite:///mlflow.db --default-artifact-root ./mlruns --host 0.0.0.0 --port 5000

dvc repro
dvc metrics show
```

Регистрация модели и алиасов — через `MlflowClient.set_registered_model_alias(...)`
(см. `build_release_manifest.py` и `app/main.py` для примеров использования).

## ДЗ Вебинар 2: доказательство воспроизводимости изменения

Изменили один параметр в `params.yaml`:

```diff
- n_estimators: 100
+ n_estimators: 200
```

И прогнали пайплайн заново — `dvc metrics diff` дал чистое, честное
сравнение "было → стало":

| Path | Metric | HEAD | workspace | Change |
|---|---|---|---|---|
| metrics.json | roc_auc | 0.90002 | 0.9008 | +0.00079 |

Новый прогон залогирован в MLflow как отдельный run (`9e6b54db19fd4be4ad6968650008e009`),
зарегистрирован как версия 2 модели `credit-model`, и продвинут через алиас
`staging` (алиас `production` при этом остался на версии 1 — так модели
обычно продвигают в проде: сначала на staging, потом, после проверки,
переключают `production`).

Итоговый паспорт релиза, тянущий все эти факты воедино (git SHA, DVC-хэши
данных/кода/модели, MLflow run + версия + алиасы, тег Docker-образа) —
в `release_manifest.json`, генерируется скриптом `build_release_manifest.py`
из реальных источников (без ручного ввода значений).

## CI vs CD

`.github/workflows/ci.yml` — это **CI** (continuous integration): каждый push
проверяет, что код + пайплайн + образ вообще собираются и работают
(repro, drift gate, smoke-test контейнера). Единственный шаг, который что-то
*публикует* — пуш образа в GHCR — выполняется только на ветке `main` и не
разворачивает сервис ни в каком окружении (ни staging, ни prod), поэтому
даже с этим шагом workflow не дотягивает до **CD** (continuous delivery/
deployment): нет ни автоматического деплоя, ни отдельного approve-шага для
выката, ни обновления работающего окружения по этому пушу.
