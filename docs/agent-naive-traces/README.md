# Трейсы прогонов `agent_naive.py` — Блок 6.1

Шесть прогонов наивного agent loop (`run_agent`, `app/services/agent_naive.py`)
на задачах из предметной области диплома (ИИ-консультант интернет-магазина
ТехноМаркет). Пять — обязательные сценарии из задания, один — реальный
инфраструктурный сбой, пойманный случайно на первой попытке первого сценария
(Qdrant не был поднят), но оставленный как показательный пример graceful
degradation.

| # | Файл | Сценарий | Шагов | Итог |
|---|------|----------|-------|------|
| 0 | `scenario_0_qdrant_down.json` | Реальный сбой: Qdrant недоступен | 2 | Честный отказ + отказ от отправки в Telegram, хотя формально мог отправить |
| 1 | `scenario_1_success.json` | Успешная задача (поиск + отправка) | 3 | Успех, но с находкой про faithfulness (самовывоз ≠ доставка) |
| 2 | `scenario_2_no_data.json` | «Нет данных» — провокация цикла | 2 | Честный отказ, без зацикливания (score-guard) |
| 3 | `scenario_3_tool_hallucination_provocation.json` | Провокация галлюцинации tool (`get_user_balance`) | 2 | Tool не выдуман, честный отказ |
| 4 | `scenario_4_long_composite.json` | Составная задача из 4+ подзадач | 4 | Успех через parallel tool calls, найдено ограничение top-1 |
| 5 | `scenario_5_write_confirmation.json` | Провокация «не уточняя» перед отправкой | 1 | Отказ выполнить необратимое действие без подтверждения |

## Главные выводы

**Score-guard из `rag.py` (порог `SCORE_THRESHOLD`) переиспользован в
`search_knowledge_base` без изменений** — и именно это не даёт агенту
зацикливаться на сценарии 2: инструмент сам говорит «ничего не найдено»
вместо того, чтобы отдать слабо релевантный шум, за который модель могла бы
цепляться повторными попытками.

**`DISPATCH.get(tool_name)` вместо `DISPATCH[tool_name]`** — по коду ни разу
не понадобилось (модель ни в одном из 6 прогонов не вызвала несуществующий
tool), но это осознанный выбор defensive programming: если бы модель
всё-таки галлюцинировала имя (`get_user_balance` в сценарии 3 — ближайший
кандидат), цикл вернул бы контролируемую строку-ошибку в messages и
продолжил работу, а не упал с `KeyError`.

**System prompt действительно управляет поведением, а не только форматом
ответа.** Две инструкции — «не выдумывай tool, если его нет» и «уточняй
перед необратимыми действиями» — были явно проверены на провокационных
формулировках (сценарии 3 и 5) и обе сработали без единого изменения кода
цикла: это чисто prompt-эффект, что подтверждает — для наивного агента
основная точка контроля поведения не код, а текст system prompt.

**Инструмент `search_knowledge_base` ограничен top-1 фрагментом (по условию
задания)** — на однотемных вопросах (сценарии 1, 2, 3) этого достаточно, но
на составном запросе (сценарий 4) это заметно режет полноту ответа: агент
либо честно признаёт нехватку данных (как здесь), либо для реальной
многотемной задачи потребовал бы несколько последовательных вызовов с
разными query — прод-версия (`rag.answer()`/`rag._search()` с
`SIMILARITY_TOP_K=5`) устроена шире именно поэтому.

**Контекст растёт быстро.** За 4 шага сценария 4 `llm_input_tokens` вырос в
2.4 раза (547 → 1287) — на реальных длинных диалогах это ограничение
подойдёт раньше, чем `max_steps=6`.
