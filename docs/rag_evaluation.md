# Оценка качества и мониторинг RAG

ДЗ 5.6, чекпоинт 5. Отчёт по числам из `tests/eval/results/` — ничего не по памяти, все цифры скопированы напрямую из сохранённых CSV/JSON.

## 1. Конфигурация

Финальная (победившая по итогам экспериментов A и B) конфигурация продового RAG-сервиса (`app/services/rag.py`):

| Параметр | Значение |
|---|---|
| Модель генерации | `gpt-4o-mini`, `temperature=0` |
| Модель эмбеддингов | `text-embedding-3-small` |
| Векторная БД | Qdrant, коллекция `technomarket_v2`, cosine distance |
| Chunking | наивный посимвольный сплит, `chunk_size=512`, `overlap=64` (`scripts/ingest.py`) |
| top_K | 5 (`RAG_SIMILARITY_TOP_K`) |
| Re-ranker | не используется |
| Score-guard threshold | 0.30 (`RAG_SCORE_THRESHOLD`) |
| Контекст для генерации | **`full`** — полный текст найденного чанка (`RAG_CONTEXT_MODE`, победитель эксперимента B) |

Судья для RAGAS-метрик (`app/eval/metrics.py`, используется только в eval, не в проде):

| Параметр | Значение |
|---|---|
| Judge LLM | `gpt-4o-mini`, провайдер OpenAI |
| Judge embeddings | `text-embedding-3-small` |

Осознанное отклонение от методички: методичка по умолчанию предлагает `claude-sonnet-4-6` через `anthropic`-клиент. В проекте уже есть `OPENAI_API_KEY` и он используется и в проде, и для судьи — заводить отдельный Anthropic-ключ и зависимость `anthropic` не было смысла. Prod-LLM (`gpt-4o-mini`) и judge-LLM здесь совпадают по имени модели, но это две независимые роли с разными системными промптами — их вызовы происходят в разных модулях (`app/services/rag.py` vs `app/eval/metrics.py`) и не влияют друг на друга.

Трейсинг: Arize Phoenix (`docker-compose.yml`, сервис `phoenix`, порт 6006), экспорт по OTLP/HTTP. Методичка описывает регистрацию `LlamaIndexInstrumentor`, но прод-RAG в этом проекте не использует LlamaIndex (сырой Qdrant + OpenAI SDK) — вместо него используется `openinference-instrumentation-openai` (авто-инструментирует реальные вызовы OpenAI) плюс ручные span'ы вокруг retrieval-шага и всего RAG-запроса (`app/observability/tracing.py`, `app/services/rag.py`). Итоговое дерево спанов в Phoenix (`retriever` → `LLM`/`embedding`) идентично тому, что дал бы `LlamaIndexInstrumentor`, если бы проект использовал LlamaIndex.

## 2. Golden dataset

- 33 пары вопрос/ответ (требование — минимум 30), файл `tests/eval/golden_dataset.json`.
- Сгенерирован через RAGAS `TestsetGenerator` на корпусе `data/` (`scripts/generate_testset.py`), сырой результат — `tests/eval/golden_dataset_raw.csv`.
- Пройден вручную: удалены дубли и слишком общие вопросы, поправлен `reference` там, где генератор промахнулся мимо содержимого корпуса.
- Поля: `user_input`, `reference`, `reference_contexts`.

## 3. Baseline

Прод-конфигурация "как есть" на момент начала ДЗ: `chunk_size=512`, генерация из 200-симв. сниппета (позже выяснилось — это баг, см. раздел 5).

Файл: `tests/eval/results/2026-08-29_1555_baseline.csv` / `.json`, 33 строки.

| Метрика | Значение |
|---|---|
| faithfulness | 0.6636 |
| answer_relevancy | 0.5248 |
| context_precision | 0.7510 |
| context_recall | 0.8995 |
| has_citation | 0.6667 |
| latency (среднее, `rag_latency_ms`) | 1324.4 мс |

## 4. Эксперимент A: chunking

Гипотеза: `chunk_size` 512 → 1024 (тот же `overlap=64`) улучшит retrieval за счёт более цельных фрагментов текста.

Пересчитан индекс в отдельную коллекцию `technomarket_v2_chunk1024` (`scripts/ingest.py --collection technomarket_v2_chunk1024 --chunk-size 1024 --overlap 64`), тот же golden dataset, тот же режим генерации (`snippet`, как в baseline — меняем только один параметр).

Файл: `tests/eval/results/2026-08-29_1703_chunk_1024.csv` / `.json`, 33 строки.

| Вариант | faithfulness | answer_relevancy | context_precision | context_recall | has_citation | latency (мс) |
|---|---|---|---|---|---|---|
| baseline (chunk_size=512) | 0.6636 | 0.5248 | 0.7510 | 0.8995 | 0.6667 | 1324.4 |
| chunk_size=1024 | 0.4531 | 0.3722 | 0.8214 | 0.9419 | 0.4848 | 1289.7 |

**Итог: побеждает baseline (chunk_size=512).** Retrieval-метрики (context_precision, context_recall) у `chunk_1024` действительно выросли — крупные цельные фрагменты находятся точнее. Но faithfulness, answer_relevancy и has_citation заметно просели. Причина видна в разделе 5: генерация в этой конфигурации всё ещё строит промпт из 200-символьного сниппета независимо от размера чанка — при `chunk_size=1024` эти 200 символов покрывают вдвое меньшую долю чанка, чем при 512. То есть улучшение retrieval никак не доходит до модели при генерации, а обрезка становится только хуже. `chunk_size=512` остаётся рабочей конфигурацией.

## 5. Эксперимент B: retrieval/generation (context mode)

Второй эксперимент выбран не из готового списка методички (top_K, re-ranker, смена модели, промпт A/B), а по прямому сигналу из данных: диагностическая матрица (низкий faithfulness + высокий context_recall = generation-проблема) в baseline указывала именно на generation, а не на retrieval — context_recall уже был 0.8995, а faithfulness всего 0.6636. Разбор кода (`_build_context()` в `app/services/rag.py`) подтвердил конкретную причину: промпт для генерации строился из тех же 200-симв. сниппетов, что и отображаемые в чате источники, а не из полного текста найденного чанка — модель физически не видела большую часть найденного контекста.

Фикс: `CONTEXT_MODE` — при `"full"` промпт строится из полного текста чанка вместо сниппета (тот же retrieval, тот же `chunk_size=512`, меняется только один параметр — источник текста для промпта генерации).

Файл: `tests/eval/results/2026-08-29_1709_full_context.csv` / `.json`, 33 строки.

| Вариант | faithfulness | answer_relevancy | context_precision | context_recall | has_citation | latency (мс) |
|---|---|---|---|---|---|---|
| baseline (snippet) | 0.6636 | 0.5248 | 0.7510 | 0.8995 | 0.6667 | 1324.4 |
| full context | 0.8782 | 0.7483 | 0.7719 | 0.9040 | 0.9091 | 1588.7 |

**Итог: побеждает `full` с явным отрывом.** faithfulness +32% (0.664 → 0.878), answer_relevancy +43% (0.525 → 0.748), has_citation +36% (0.667 → 0.909). Retrieval-метрики практически не изменились (это ожидаемо — retrieval не менялся), что подтверждает: проблема была именно в генерации, а не в поиске. Цена — рост latency на 265 мс (1324 → 1589 мс), что признано приемлемым (более длинный промпт на входе модели).

## 6. Финальный конфиг и числа

**Беру вариант `chunk_size=512` + `CONTEXT_MODE=full`**, потому что на golden dataset это единственная из трёх проверенных конфигураций, которая проходит оба порога чекпоинта:

| Метрика | Значение | Порог чекпоинта | Пройден? |
|---|---|---|---|
| faithfulness | 0.8782 | > 0.7 | ✅ |
| answer_relevancy | 0.7483 | > 0.7 | ✅ |
| has_citation | 0.9091 | > 0.95 | ❌ (см. раздел 8) |
| context_precision | 0.7719 | — | — |
| context_recall | 0.9040 | — | — |
| latency (среднее) | 1588.7 мс | — | — |

Конфигурация зафиксирована как дефолт: `app/services/rag.py` — `CONTEXT_MODE = os.getenv("RAG_CONTEXT_MODE", "full")` (было `"snippet"`), `scripts/ingest.py` — `chunk_size=512`/`overlap=64` остаются дефолтами без изменений (баг был не в них).

## 7. Failure analysis

Топ-5 худших ответов по `faithfulness` из финальной конфигурации (`2026-08-29_1709_full_context.csv`), разбор по матрице 2×2 (низкий faithfulness + низкий context_recall = retriever-проблема; низкий faithfulness + высокий context_recall = generation-проблема).

**1. "What steps are involved in transferring data from an iPhone to a Samsung Galaxy, and how does the TechnoMarket app facilitate the management of audio product orders on iOS devices?"**
faithfulness 0.0, context_recall 0.5. Ответ — score-guard fallback ("По базе не нашёл, могу эскалировать").
Диагноз: **retriever-проблема**. Вопрос составной (перенос данных + управление заказами в приложении — две разные темы). Наивный посимвольный chunking не даёт ни одного чанка, покрывающего обе темы сразу, top_score не дотянул до порога 0.30.

**2. "Как подать жалобу на качество товара и какие способы доставки доступны в ТехноМаркет?"**
faithfulness 0.25, context_recall 0.5. Модель ответила "информация отсутствует" по обеим частям вопроса.
Диагноз: **retriever-проблема** — тот же паттерн: составной вопрос, retrieval нашёл только часть релевантного контекста (про заказы, не про жалобы конкретно).

**3. "Сколько стоит Lenovo Legion 5 Pro RTX 4060 и сколько их в наличии?"**
faithfulness 0.5, context_recall 1.0, has_citation yes. Ответ: "Lenovo Legion 5 Pro RTX 4060 стоит 129 990 руб. В наличии 4 шт. [2]".
Диагноз: **generation-проблема**. Контекст найден полностью (recall 1.0), но в нём нет явного указания на GPU "RTX 4060" — модель приписала эту характеристику товару, не подтверждённую текстом чанка.

**4. "Samsung Galaxy S24 how much it cost and what features it got?"**
faithfulness 0.6, context_recall 0.5. Ответ называет конкретный процессор (Snapdragon 8 Gen 2) и ёмкость батареи (4000 мАч).
Диагноз: **смешанная** — часть контекста не найдена (recall 0.5), и вдобавок модель называет конкретные спецификации, не подтверждённые даже найденной частью контекста.

**5. "Какой MacBook лучше выбрать, если я также хочу использовать его с iPhone, и какие у них характеристики?"**
faithfulness 0.69, context_recall 0.0. Ответ подробно описывает MacBook Air M1 и MacBook Pro M3.
Диагноз: **чистая retriever-проблема**. context_recall 0.0 — найденный контекст (про приём устройств в трейд-ин) вообще не по теме вопроса. Модель ответила из общих знаний, а не из контекста — полный промах retrieval.

Итог: 3 из 5 — retriever-проблема на составных/многосоставных вопросах (naive chunking плохо режет текст по темам независимо от `chunk_size`), 1 — чистая generation-проблема (додумывание неподтверждённой характеристики), 1 — смешанный случай.

## 8. Известные проблемы и план улучшений

**has_citation ниже целевого порога (0.9091 vs > 0.95).** Модель не всегда явно проставляет маркер источника `[N]`, даже отвечая по существу. План: усилить инструкцию в `SYSTEM_PROMPT` (сейчас "Цитируй источники в формате [1], [2]" — не очень настойчиво) и/или добавить few-shot пример с цитированием прямо в промпт.

**Retrieval проседает на составных/многосоставных вопросах.** 3 из 5 худших случаев в failure analysis — вопросы с двумя разными темами в одной формулировке. Наивный посимвольный chunking режет текст без учёта структуры документа, из-за чего для составного вопроса редко находится единый релевантный чанк. План: попробовать chunking по структурным границам (заголовки/разделы markdown) вместо фиксированного числа символов, либо декомпозицию составных вопросов на подзапросы перед retrieval.

**Точечные необоснованные детали при полном контексте (пример 3 в failure analysis).** Даже при `CONTEXT_MODE=full` и recall=1.0 модель иногда добавляет правдоподобную, но не подтверждённую контекстом деталь (например, конкретную модель GPU). План: более строгая инструкция "не добавляй характеристики, не упомянутые в контексте буквально" плюс точечная проверка на подобных кейсах в следующих ревью golden dataset.

**(Опционально, шаг 9) Живой трафик: 40.9% ответов помечены как hallucinated Phoenix `HallucinationEvaluator`-ом.** Прогон на 22 живых трейсах (`tests/eval/results/2026-08-29_1335_hallucination_eval.csv`, конфигурация на момент прогона — ещё `snippet`, до фиксации `full`) дал 13 grounded / 9 hallucinated. Важная деталь: почти все hallucinated-случаи — это свободно сформулированные вопросы (не из golden dataset), на которые модель отвечает "по базе не нашёл, могу эскалировать", хотя релевантная информация в найденном контексте реально есть (пример: "Какая гарантия на наушники JBL?" — в контексте была явно указана гарантия 1 год, модель всё равно отказалась отвечать). Golden dataset генерировался RAGAS'ом из того же корпуса, поэтому его формулировки естественно ближе по структуре к тексту документов — а вот при перефразировке "своими словами" модель иногда решает, что не может ответить, хотя контекст релевантен. Это generation-проблема — вероятно, излишне буквальная трактовка инструкции "при отсутствии информации в контексте пиши 'не нашёл'" из `SYSTEM_PROMPT`. План: смягчить формулировку инструкции (например, явно указать "ищи релевантную информацию даже если вопрос сформулирован не точь-в-точь как в документе") и периодически повторять этот прогон на живом трафике как лёгкий продакшн-мониторинг, отдельно от golden-dataset метрик.

**Latency выросла на 265 мс с `CONTEXT_MODE=full`.** Приемлемо на текущем масштабе (33 golden-вопроса, единичные live-запросы), но при росте нагрузки или числа найденных чанков (top_K) стоит переоценить — рост нелинеен относительно объёма контекста в промпте.

**Шум RAGAS-метрик.** LLM-as-judge даёт разброс ±5–10% от прогона к прогону; 33 вопроса — на грани минимума (30), при повторных экспериментах в будущем стоит расширить golden dataset для более узких доверительных интервалов.

**Golden dataset содержит вопросы на смеси русского и английского языков.** RAGAS `TestsetGenerator` не гарантирует, что язык сгенерированного вопроса совпадёт с языком корпуса — часть вопросов в `golden_dataset.json` сформулирована по-английски (например, "MacBook Pro M3 how much cost?"), хотя корпус и `SYSTEM_PROMPT` — русскоязычные. Это не было отфильтровано на этапе ручного review. На посчитанные метрики это не влияет: `text-embedding-3-small` — кросс-языковая модель (английский запрос уверенно находит релевантные русскоязычные чанки), а `SYSTEM_PROMPT` явно требует отвечать по-русски независимо от языка вопроса, так что ответ всё равно на русском и оценивается judge'ом корректно. План: на будущих итерациях либо фильтровать генератор по языку явно, либо оставить как есть — смешанный язык вопросов заодно неплохо имитирует реальных пользователей.
