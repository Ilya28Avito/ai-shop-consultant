# Отчёт: agent_naive vs agent_react — Блок 6.2

5 задач из домена диплома (ИИ-консультант ТехноМаркет), каждая прогнана дважды:
на baseline (`app/services/agent_naive.py`, ДЗ 6.1, без изменений) и на новом
ReAct-агенте с лимитами и self-reflection (`app/services/agent_react.py`).
Модель в обоих — `gpt-5.4-mini`. Полные трейсы прогонов лежат рядом с
данным отчётом в git-истории коммита; здесь — сводная таблица и разбор.

## Наблюдения

**1. Self-reflection ни разу не выдал REVISE за все 5 задач.** Во всех
tool-вызовах critic вернул `OK` с первого раза. Это означает, что на этом
наборе задач вторая половина Reflexion-light (собственно ревизия и подъём до
`gpt-5.4`) ни разу не была протестирована в деле — либо задачи оказались
недостаточно провокационными для самого исполнения tool (в отличие от
провокации 5, где ловушка была не в tool, а в необходимости вообще НЕ
вызывать инструмент), либо более аккуратные tool-описания react сами по себе
не давали моделям делать те ошибки, которые critic должен был бы поймать.

**2. Наиболее ценная находка — задача 3, где naive реально ошибся.** Найденный
в базе фрагмент — это список **исключений** ("гарантия не действует, если...":
самостоятельный ремонт, программные проблемы после обновления ПО
пользователем), но naive подал его клиенту под заголовком "Условия гарантии",
не различив "что покрывает" и "что не покрывает". Модель в react сама
(без единой ревизии — critic сказал `OK`) сформулировала точнее: "Гарантия
**не действует** в случаях: ...". Разница — не в самом механизме reflection, а
в том, что более развёрнутый system prompt и tool-описания react ("используй
только то, что вернули инструменты", подробное "что возвращает" в описании
`search_knowledge_base") задают более осторожный тон генерации ещё до того,
как ошибка вообще случится. Это важный вывод для диплома: prompt engineering
самого исполнителя (main model) может предотвращать ошибки эффективнее, чем
последующая проверка критиком.

**3. Reflection — чистый оверхед на простых задачах.** На задачах 1, 2 и 5
(однотуловые/безtool-овые) react и naive дали функционально одинаковый
корректный результат, но react потратил в 1.5-1.9 раза больше токенов
(критик — это всегда +1 LLM-вызов на каждый использованный tool, даже когда
проверять нечего). В сумме по всем 5 задачам react — 11960 токенов против
7109 у naive, рост на 68%, за которые на этом наборе задач реально "куплена"
только одна исправленная ошибка (задача 3).

**4. Более строгий промпт react иногда портит UX, а не только предотвращает
ошибки.** В задаче 4 react отправил клиенту сырую ISO-строку времени
(`2026-08-30T11:05:04.895431+03:00`) вместо человекочитаемого "11:04 по
московскому времени", как сделал naive. Инструкция "не добавляй ничего
неподтверждённого" сработала настолько буквально, что модель не решилась
даже переформатировать дату для читаемости — хотя переформатирование не
меняет факт, а только форму подачи. Это стоит учесть при следующей
итерации промпта: разграничить "не выдумывай факты" и "не меняй форму
представления факта".

**5. Гипотеза задания про провокационную задачу не подтвердилась — и это
тоже результат.** Ожидалось, что naive "скорее всего" вызовет tool на
арифметической задаче, а react — нет. По факту оба агента ни разу не
дёрнули `search_knowledge_base` на простом расчёте скидки: `gpt-5.4-mini`
и без ReAct-обвязки не склонна звать инструмент там, где хватает
прямого рассуждения. Разница между агентами здесь — не в решении "звать
или не звать", а в прозрачности: react явно залогировал "thought"
("...без обращения к базе знаний"), сделав это решение видимым и
проверяемым, тогда как у naive такого явного обоснования в трейсе нет.

**6. Оба жёстких лимита (`max_iterations`, `timeout_per_iteration_sec`) не
были естественно достигнуты ни на одной из 5 задач** — ожидаемо, задачи
из домена диплома укладываются в 1-3 шага. Код путей `"Превышен лимит
итераций"` и `"Timeout"` в этом отчёте эмпирически не проверен (только
логически, чтением кода) — при необходимости для защиты диплома можно
отдельно прогнать стресс-тест (задача с заведомо избыточным числом
подзадач при `max_iterations=8`), чтобы получить трейс с реальным
срабатыванием лимита.

## Итог

На простых и типовых для магазина задачах (1, 2, 4, 5) `agent_naive` и
`agent_react` дают одинаково верный результат — разница только в
прозрачности решений (`thought` в трейсе) и в токенах (react дороже на
50-90%). Единственная задача, где разница действительно на пользу react —
задача 3, но и там сработал не сам механизм self-reflection (ревизий не
было), а более осторожный prompt/tool-дизайн главного исполнителя. Честный
вывод: на этом наборе из 5 задач ReAct-обвязка с лимитами уже окупается
как страховка от конкретной ошибки faithfulness (задача 3) и как источник
аудируемости (`thought`, `critic_verdict` в каждом шаге), но её самый
дорогой компонент — сам self-reflection-цикл — пока не набрал ни одного
случая, где он был бы строго необходим; для полной проверки этой части
нужен более провокационный набор задач с реально "грязными" tool-результатами.
